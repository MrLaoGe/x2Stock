# 旧数据选择性迁移设计

状态：阶段 0 设计；尚无迁移程序、已导入数据或已验证回滚。默认不迁移旧数据；用户选定模块后，按[数据中心模块](../modules/data-center.md)评估并另批授权；下一本体任务是[骨架](../modules/application-skeleton.md)，不实现导入，审计输入见[旧资产快照](legacy-audit.md)，字段遵循[接口契约](../contracts.md)。

## 输入与隔离

迁移是用户选定模块、数据集、字段、证券/日期范围及批次后另行批准的本地操作。共有功能、旧表存在、审计规模和评估结果都不是执行授权。流程为用户选模块 → 明确新版功能 → 定义所需数据 → 评估旧数据价值 → 按需另批导入。数据库结构升级由 Alembic 显式管理，不等于旧数据导入。旧路径只作为临时输入，新版运行、采集、任务和查询不依赖旧项目。旧SQLite、DuckDB与文件以只读方式读取；禁止 import 旧应用、数据库初始化或调度入口。旧服务持续写入时，使用经验证的一致性导出或稳定快照；不可把正在写入的数据库文件复制当作一致性保证。

新版使用独立PostgreSQL、独立数据目录、配置、密钥与worker，见[架构](../architecture.md)。首期每条持久数据及后台任务携带 `user_id`、`workspace_id`，默认对应配置的 `local/local`；由服务端可信本地身份上下文确定，不能信任请求正文随意改变归属。配置见[配置说明](../configuration.md)。

没有固定首批迁移目标，旧 8,991,131 行日行情仅是参考快照。逐数据集确定功能需求、字段、证券/日期范围、粒度、单位、时效、留存与验收，并比较新采集、有限旧导入、新版重算或不支持。未选模块不建业务表、不部署采集/导入任务；模块须可在无旧项目时独立运行，新采集满足需求即可上线，不等待可选迁移。历史缺失若限制功能须真实显示。

不自动复制旧配置、调度器、待执行任务或 AI 报告；旧指标在新版重算。只为已选范围设计映射，不提前实现通用搬库工具。以下快照、批次和回滚规则在启用导入时生效，不强加骨架。

## 接受规则与缺口

- 只允许 Tushare、东方财富、财联社；排除 zhitu、mairuiapi、新浪、同花顺等未授权来源，禁止通过改名绕过规则。
- 记录来源、字段来源和依赖链均明确时才接受。未知来源、笼统标签、不可分的混合来源拒绝；输出拒绝原因与数量，不把原始拒绝内容复制到新版资产区。
- 可拆分字段仅保留具有允许来源证据的部分，其余为空。原始、规范、派生、AI结果分开；旧指标与派生结果不作为新版计算结果继承，按新版口径重算；输入事实仍须完整依赖证据。
- 自然键至少包含归属、数据集、交易所证券标识、业务日期/时点及调整语义；成员数据另含分类、板块标识和有效区间，不能仅按名称合并。
- 质量校验包含单位、日期、OHLC关系、非负量额、重复与覆盖；异常保持隔离，缺失不写零，低覆盖不假装完整。
- 历史 `available_at` 不可证明时保持未知并标记量化限制；事件时间、旧采集时间、迁移时间分别保留。导入不创造历史可用时间。

允许来源标签不是真实性证明。预检输出必须区分“来源符合”“结构/质量通过”和“point-in-time已证明”，不把三者合并为一个绿色状态。

## 批次、断点与幂等

流程为 **只读预检 → 独立 staging → 校验 → 发布 → 验收**。默认先预检，不写新版正式数据；预检本身需获评估任务授权；发布需要用户选定模块、数据集、字段、证券/日期范围和批次并另行批准导入，接口统一使用规划中的 `/api/v1`，详情后续按[接口契约](../contracts.md)细化。

每批登记归属、源快照摘要、数据集、映射/规则版本、状态、记录计数和非敏感问题摘要。日志不记录密钥、带凭据请求或私人正文；完整源路径只保存在本地受限迁移元数据，不返回普通前端响应。

- 断点用稳定快照标识、表/文件与业务键游标登记；按确定排序分页，不使用动态旧库的offset作可靠断点。
- 每个staging块写入与检查点推进在同一事务完成；失败重跑按批次和源记录标识幂等，不产生重复块或漏读。
- 源快照或映射版本改变时建立新批次，禁止复用旧断点。重复导入相同快照、规则及内容不创建相同业务版本。
- 验收记录扫描、接受、拒绝、缺失、发布、新增、冲突与跳过数量，并校验分块摘要和全局计数。冲突列表不泄露个人内容。

在发布前将允许记录转为不可变数据revision，并关联原始来源证据。正式业务键维护 `active_revision_id`；staging不能被研究查询读取。发布前锁定对应键，已存在的有效采集数据默认优先，旧导入不得覆盖已有有效新数据；出现冲突记为跳过，待明确的修复任务处理。

## 不破坏后续采集的回滚

采用“不可变revision＋正式指针＋发布journal”保护回滚，不按 `import_batch_id` 直接删除正式行。

1. 发布journal逐键保存发布前指针、导入revision及批次。正常采集或人工修正生成新的revision，并更新正式指针，不能在导入revision上原地改内容。
2. 回滚在事务内锁定键并比较当前指针；**只有当前仍指向本批次发布的revision**，才恢复发布前的有效指针。原来没有数据则移除该键的正式指针。
3. 当前指针已被采集、修正或另一有效批次替换时，保持当前值，记录 `superseded`；不得用旧快照覆盖或删除更新后的数据。
4. 被恢复的旧revision须仍为有效版本。若原指针所属批次已撤销，沿journal查找最近有效前序版本；没有则移除指针，不能复活已撤销的数据。
5. 批次撤销标记、逐键结果与指针修改事务一致。回滚幂等、可重试；审计revision先保留，回收须检查无正式指针和有效依赖引用。

启用该导入能力的数据集，其后续采集和修正写入必须遵守同一revision规则，否则回滚保证不成立。新版衍生计算需通过输入revision关联单独失效，不能级联删除与新数据重算有关的结果。发布journal与回滚依据保存在新版，不依赖旧库继续存在。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 允许事实、排除来源、未知来源混存 | 只接受证明完整的允许部分；拒绝原因可核对 |
| 相同快照重复导入 | 无重复业务数据或revision；统计一致 |
| 分块中断后重跑 | 已提交块不重复，未提交块重新处理，数量守恒 |
| 快照或映射改变后续跑 | 旧断点被拒绝，建立新批次 |
| 暂存与发布之间查询 | 只能读取正式有效revision |
| 批次发布后原样回滚 | 恢复前序有效指针，重复回滚不改变结果 |
| 导入后正常采集更新同一键，再回滚 | 采集revision保留，记录superseded |
| 并发采集与回滚 | 事务和指针比较避免覆盖更新，无部分状态 |
| 先撤销前序批次、再撤销后序批次 | 不复活已经撤销的前序版本 |
| user/workspace不同、跨归属任务查询 | 不能读、发布或回滚另一归属数据 |
| 旧项目缺席，新版常规查询/采集 | 正常运行，不尝试读取旧路径 |
| 2019行情有价格但缺因子/可用时间 | 明示缺口，不未来填权，不宣称可做无偏回测 |

分别记录功能状态、数据取得状态和迁移状态；迁移可为未选、评估中、待授权、已授权待实现、已验收或失败，不把功能完成自动写成迁移完成。未知历史 `available_at` 持续保留量化限制，即使导入数量验收通过也不能消除。

验收采用合成fixtures；真实数据只在用户本地核验。阶段 0 仅固定这些行为约束，后续实现时补充schema迁移、作业状态机、失败恢复和测试证据。
